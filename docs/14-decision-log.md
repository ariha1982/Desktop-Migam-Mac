# 14. 설계 결정 기록

## 작성법

큰 기술 선택이나 범위 변경마다 아래 템플릿을 복사한다.

```text
### ADR-XXX — 제목

- 날짜:
- 상태: 제안/채택/폐기/대체
- 상황:
- 결정:
- 이유:
- 장점:
- 단점:
- 후속 작업:
```

## ADR-001 — Tauri 2 + Rust 유지

- 날짜: 2026-08-23
- 상태: 채택
- 상황: 기존 설계가 Tauri 2 + Rust 앱 확장을 전제로 한다.
- 결정: 데스크톱 셸과 시스템 로직은 Tauri 2 + Rust를 유지한다.
- 이유: 기존 기준과 Windows API 연동을 재사용하고 24시간 내 기술 전환 위험을 피한다.
- 장점: 작은 번들, Rust 테스트, 네이티브 API 경계 명확화.
- 단점: 투명 창과 Win32 세부 동작 검증 필요.

## ADR-002 — 전체 화면 오버레이를 사용하지 않음

- 날짜: 2026-08-23
- 상태: 채택
- 상황: 전체 화면 투명 창은 클릭 방해와 합성 비용이 크다.
- 결정: 펫 주변 크기의 작은 창을 이동한다.
- 이유: 입력 방해와 GPU 사용을 줄인다.
- 단점: 창 위치 업데이트와 좌표 변환이 필요하다.

## ADR-003 — 설정을 JSON으로 원자 저장

- 날짜: 2026-08-23
- 상태: 채택
- 상황: MVP 설정 규모가 작고 관계형 쿼리가 필요 없다.
- 결정: app data의 JSON 파일을 tmp write 후 교체한다.
- 이유: 구현이 단순하고 사람이 복구하기 쉽다.
- 단점: 동시 write 제어와 migration이 필요하다.

## ADR-004 — 사이트 감지는 창 제목만 사용

- 날짜: 2026-08-23
- 상태: 채택
- 상황: 브라우저 URL 접근은 확장 프로그램이나 접근성 API가 필요하다.
- 결정: 프로세스명과 창 제목 포함 문자열만 지원한다.
- 이유: 개인정보 범위와 구현 시간을 제한한다.
- 단점: 제목이 숨겨지거나 바뀌면 감지하지 못한다.

## ADR-005 — 불확실한 창은 보호

- 날짜: 2026-08-23
- 상태: 채택
- 상황: 관리자 권한과 시스템 창은 정보 읽기나 제어가 실패할 수 있다.
- 결정: 정보가 부족하면 최소화하지 않는다.
- 이유: 생산성 기능보다 사용자 안전이 우선이다.
- 단점: 일부 방해 앱을 놓칠 수 있다.

## ADR-006 — 프런트 전역 상태 라이브러리 미사용

- 날짜: 2026-08-23
- 상태: 채택
- 상황: 창별 UI가 작고 핵심 상태는 Rust에 있다.
- 결정: React Context와 reducer로 시작한다.
- 이유: 의존성과 상태 중복을 줄인다.
- 재검토 조건: 화면과 편집 상태가 크게 늘어날 때.

## ADR-007 — MVP 프런트엔드는 순수 TypeScript 사용

- 날짜: 2026-08-23
- 상태: 채택, ADR-006의 React 언급을 대체
- 상황: 화면이 펫·타이머·설정으로 작고 핵심 상태는 Rust에 있다.
- 결정: React를 추가하지 않고 Vite + TypeScript + DOM API로 구현한다.
- 이유: 기존 골격을 보존하고 24시간 MVP의 의존성과 전환 비용을 줄인다.
- 재검토 조건: 복잡한 화면 조합과 재사용 컴포넌트가 실제로 크게 늘어날 때.
